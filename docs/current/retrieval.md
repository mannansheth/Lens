# Retrieval and answer generation

Lens retrieves from its project-scoped PostgreSQL index using lexical search and dense-vector similarity. Hybrid search combines candidates from both paths, applies query-aware ranking signals, and can expand selected evidence through statically discovered relationships. `alpha` weights normalized lexical versus vector scores in the hybrid score; additional exact-identifier, source-scope, entity-kind, document-topic, and navigation/relationship signals also influence ordering. The hybrid score by itself is not the final rank. Search debug output exposes candidate scores and signals so retrieval decisions can be inspected. See [How Lens understands a project and answers questions](rag-pipeline.md) for the full theoretical explanation and end-to-end flow.

For questions about how behavior flows across files, evidence expansion follows resolved edges within depth and context limits. Unresolved relationships are retained as uncertain references rather than treated as established calls. Context construction selects bounded excerpts, source locations, relationship descriptions, and compact citation identifiers. The answer provider receives this context instead of the entire repository. Documentation can be selected alongside code; document dates/status are source metadata and do not independently establish freshness.

The answer layer supports the Ollama adapter and optional Gemini adapter. It requests structured output, validates response shape, intent, and citations, then maps citations back to file paths and lines. This validation catches malformed or unsupported structures but cannot prove semantic entailment for every claim. Static analysis also cannot establish live state, runtime authorization, or execution success.

Use `lens search ... --debug` to inspect retrieval and `lens ask ... --json` to inspect structured answers. Retrieval recall and citation validity should be evaluated separately from answer correctness and usefulness. See [validation](validation.md).
